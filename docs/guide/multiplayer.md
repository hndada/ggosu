# 멀티플레이 서버와 네이티브 싱크

`cmd/multi`는 독립 HTTP/WebSocket 서버다. 방·경기 상태는 서버가 관리하고 입력·판정·오디오는
클라이언트가 처리한다. 네이티브 `cmd/game`은 실제 게임을 로드한 뒤 서버에 접속하며,
공통 시작 예약과 상대의 기준 시각에 맞춘 점수 비교를 지원한다.

방 채팅은 웹/네이티브 모두 오른쪽 접이식 패널로 제공한다. 동작과 검증 범위는 [방 채팅](chat.md)을 참고한다.

데스크톱 곡 선택창의 **멀티플레이**에서 서버 접속·방 생성/입장·곡 선택/제안·Go를 사용할 수 있다.
관전 플레이 장면, 프로필, 공식 랭킹은 미구현이다. 브라우저 WASM 게임의 멀티 참가는 아직 지원하지 않는다.
멀티방의 채보 확보는 편의 기능으로 별도 취급한다. 이번 싱크 구현은 로컬 파일을 사용하며
다운로드·업로드·외부 링크 연동을 추가하지 않았다. 공식 미러의 기준은 ggosu가 운영하는 저장소다.

## 실행

```powershell
go build -o build/bin/multi.exe ./cmd/multi
go build -o build/bin/game.exe ./cmd/game
.\build\bin\multi.exe -addr 127.0.0.1:8090
```

데스크톱에서는 `gosu.exe`의 **멀티플레이**에서 `ws://127.0.0.1:8090/ws`와 닉네임을 입력한다.
방장은 로컬 채보와 Time Rate·Pitch·Mods를 선택하고, 다른 사람은 곡을 제안할 수 있다.
방장의 **Go**는 선택 채보를 가진 접속자를 모두 참가시킨다. 수동 준비 버튼은 없으며
로딩과 시계 동기화 완료는 게임이 내부적으로 보고한다. 채보가 없는 사람과 경기 도중 입장자는 대기한다.

대기실 연결이 방 인원을 소유한다. 게임은 30초 만료·한 번만 사용할 수 있는 연결 티켓으로
동일 인원에 붙으므로 별도 슬롯을 소비하지 않는다. 게임 종료·완주·포기 후에도 방과 채팅은 유지된다.
결과의 **다음 곡 대기**로 방장이 다음 곡을 선택할 수 있고, **플레이 포기 · 대기실**은
자기 게임만 종료한다. **방 나가기**와 **연결 종료**는 방 멤버십을 해제한다.
**곡 목록으로**는 패널만 닫는다. 서버 접속과 오른쪽 채팅은 유지된다.

## 비밀번호 방

방 만들기의 **비밀번호 (선택)**를 비워 두면 공개 방이며, 입력하면 비밀번호 방이다.
목록의 🔒 표시를 누르면 비밀번호 입장창을 연다. 잘못된 비밀번호는 창 안에 오류를 표시하고 다시 입력할 수 있다.
입장 확인 중에는 중복 제출과 취소를 막으며, 확인이 끝나면 입력칸을 비운다. 공개 방은 바로 입장한다.
비밀번호는 대소문자와 앞뒤 공백을 구분하며 제어 문자를 제외한 최대 64자다. 로컬 설정에는 저장하지 않는다.

서버가 비밀번호를 확인한 뒤에만 방 멤버로 추가한다. HTTP·WebSocket 방 목록과 방 상태에는
`locked` 여부만 표시하며 비밀번호·salt·검증용 값은 보내지 않는다. 방마다 무작위 16바이트 salt와
PBKDF2-HMAC-SHA256(600,000회)의 32바이트 검증 값을 메모리에 보관한다. 평문을 방에 보관하지 않는다.
검증 계산은 방 상태 락 밖에서 최대 네 개까지 진행하며, 입장 직전에 방과 멤버십을 다시 확인한다.

방장 승계 뒤에도 같은 비밀번호를 사용한다. 비밀번호 변경·해제는 현재 제공하지 않는다.
입장한 대기실의 게임 프로세스는 기존 한 번용 연결 티켓으로 붙으므로 비밀번호를 다시 입력하거나 전달하지 않는다.
방은 기존처럼 마지막 인원이 나가거나 서버가 재시작되면 사라진다. 원격 운영에서는 아래 안내의 WSS 연결을 사용한다.

## CLI 접속

별도 터미널에서 방장을 실행한다. 실제 채보·에셋·이미지·게임 화면을 준비한 뒤 방을 생성하고 준비 상태가 된다.

```powershell
.\build\bin\game.exe -chart songs/demo/demo.osu -multi ws://127.0.0.1:8090/ws -name Host
```

게임 화면 상단과 표준 출력의 `multi room: ...`에서 방 ID를 확인한다. 다른 PC는 같은 채보 파일과 에셋을
갖고 다음처럼 참가한다. `SERVER`는 해당 PC에서 접속할 수 있는 서버 주소로 바꾼다.

```powershell
.\build\bin\game.exe -chart songs/demo/demo.osu -multi ws://SERVER:8090/ws -room ROOM_ID -name Guest
```

CLI에서는 최소 두 명이 준비되면 방장이 F5로 시작한다. `-multi-start`는 전원 준비 후 한 번 자동 시작하는 검증용 옵션이다.
비밀번호 방을 CLI로 만들거나 들어갈 때는 같은 `-room-password "비밀번호"`를 지정한다.
데스크톱 대기실에서 시작한 게임은 연결 티켓을 사용하므로 이 옵션이 필요 없다.
Esc는 퇴장/포기, PgUp/PgDn은 표시 스크롤 조절이다. 경기 중 개인 일시정지(P)와 배속 변경(F7)은 비활성이다.
라이브 플레이가 포커스를 잃으면 포기 처리하며, Auto는 검증용으로 백그라운드 실행할 수 있다.
저장된 리플레이를 멀티 참가자로 실행하는 모드는 지원하지 않는다. Auto/클라이언트 보고 점수를 공식 랭킹으로 쓰지 않는다.

방은 2~8명이다. 마지막 접속자가 나가면 삭제하고, 방장이 나가면 남은 참가자에게 승계한다.
방과 결과는 메모리에만 보관한다. 서버가 재시작되면 사라지며 재접속·이미 시작된 경기의 플레이 참가는 미구현이다.
외부 호스팅·TLS·DNS·방화벽 설정은 하지 않았다. 원격 운영은 HTTPS/WSS와 WebSocket Upgrade 전달이 필요하다.

서버 옵션은 `-clients 256`, `-rooms 128`, `-start-delay 3s`, `-finish-grace 30s`가 기본이다.
네이티브는 Origin 없이 접속하고 브라우저는 같은 호스트의 Origin을 기본 허용한다.
다른 사이트에서 접속하려면 `-origins`에 정확한 HTTP/HTTPS Origin을 쉼표로 구분해 지정한다.
이 목록은 기본 허용 범위를 대체하며 Origin 검사는 계정 인증이 아니다.

## 시간 동기화와 시작 예약

프로토콜 버전은 **6**다. Visibility와 비밀번호 입장 조건을 확인하므로 이전 클라이언트와 서버를 함께 쓰지 않는다.
게임 시간에는 Windows QPC를 사용하고, 서버도 `internal/clock.Counter`를 사용한다.
서버의 UTC `start_at`은 표시용이다. 실행 예약과 보고 검사는 프로세스 기준 단조 시각 `start_ns`를 사용한다.
Windows Go 1.25 런타임의 `time.Since` 시계와 QPC를 섞었을 때 음수 RTT 표본을 관측하여 서버도 QPC로 통일했다.

시계 요청은 네 시각을 사용한다.

- t1: 클라이언트 socket writer가 JSON 전송 직전에 기록.
- t2: 서버가 프레임을 읽은 직후 기록.
- t3: 서버 socket writer가 응답 전송 직전에 기록. 응답 큐 대기를 포함해 처리 시간을 제거한다.
- t4: 클라이언트가 프레임을 읽은 직후, 게임/입력과 같은 QPC로 기록.

```text
server-minus-client offset = ((t2-t1) + (t3-t4)) / 2
network RTT = (t4-t1) - (t3-t2)
local start = server start - estimated offset
```

최근 30초 이내 표본을 최대 16개 보관하고, RTT가 작은 세 표본의 offset 중앙값을 사용한다.
불확실성은 선택한 표본의 RTT 절반과 offset 분산으로 보수적으로 표시한다. 비대칭 경로 오차는 제거되지 않는다.
잘못되거나 2초 이상 지연된 표본은 버리고 추가 측정한다. 클라이언트는 최소 세 유효 표본과
100ms 이하 추정 불확실성을 요구한다. 이 상한은 접속 정책이지 100ms 싱크 정확도 보장이 아니다.

```text
lobby: 채보·플레이 조건 선택, 보유 여부 자동 확인, 곡 제안
→ preparing: Go 시점의 채보 보유자를 참가자로 고정, 게임 로딩·시계 측정 (최대 30초)
→ arming: 서버가 미래 시작 시각과 새 경기 ID를 배포
→ armed: 각 클라이언트가 로컬 QPC 시작 예약을 확인
→ playing: 참가자 전원의 예약 확인 후 서버가 경기 시작을 확정
→ finished: 전원이 완료/포기/이탈/타임아웃
```

서버의 확인 마감은 시작 500ms 전(짧은 start-delay에서는 대기 시간의 1/3 전)이다.
누락·늦은 확인·확인 중 이탈이면 대기실로 취소하고 준비를 해제한다. 이전 경기 확인은 새 경기로 적용되지 않는다.
클라이언트는 예약 여유가 100ms 미만이거나 시작 확정을 100ms 이상 늦게 받으면 뒤늦게 플레이를 시작하지 않는다.
네트워크 단절이 있는 분산 환경에서 모든 PC의 동시 실행을 절대 보장하는 프로토콜은 아니다.

게임의 Timeline 시작 원점은 첫 Update 시각이 아니라 **예약된 QPC 시각**이다.
첫 프레임이 조금 늦어도 현재 곡 위치부터 진행하고 원래 입력/리플레이 `game-1x` 좌표를 유지한다.
곡 중 시계 표본은 드리프트 관측용이며 고정된 경기 시간축을 점프하거나 배속을 조정하지 않는다.

오디오는 원본 곡 시간축을 유지한다. 예정된 BGM 플레이어를 미리 준비하고 250ms 앞의 항목을 최대 32개씩 준비한다.
늦은 프레임의 BGM 시작은 경과 위치로 seek하여 프레임 지연을 소프트웨어상 보정한다.
이는 물리 출력 지연 보정이 아니다. 다른 PC, 스피커·헤드폰·Bluetooth 출력의 실제 시간 차이는 측정하지 않았다.

## 시각별 점수 이력 비교

점수가 바뀔 때 `(시각, 누적 Score)`를 기록한다. 별도의 고정 시간 버킷이나 점수 보간은 사용하지 않는다.
원본 채보 기준 시각은 `game position - personal judgement offset`이다.
0ms와 80ms 개인 판정 오프셋으로 플레이해도 같은 원본 시각의 점수 변화를 비교할 수 있다.

상대의 `(score_at_ns, score)`가 오면 내 이력에서 **그 시각 이하의 가장 최근 점수**를 이진 검색한다.
내 최신 HUD는 그대로 유지하고, 상대 비교에는 해당 과거 점수만 사용한다. 수신 시각과 RTT로 점수를 추정하지 않는다.
상대 시각이 내가 처리한 watermark보다 앞서 있으면 Pending으로 표시한다.
전부 판정한 완주 점수에 한해서, 오프셋으로 다른 참가자의 종료 시각이 조금 뒤에 있는 구간도 최종 점수가 고정됐음을 확인해 비교한다.

판정 콜백의 시각은 점수가 실제 반영된 `Session.Input/Advance`의 게임 시각이다.
예를 들어 프레임 정지 후 처리한 MISS를 과거 노트 시각으로 소급해 기록하지 않는다.
그래서 처리 지연이 큰 PC의 중간 점수에는 실제 지연이 드러나며, 이런 지연까지 과거 점수를 만들어 숨기지는 않는다.
같은 시각 비교는 네트워크 도착 지연을 해결한다. 모든 프레임 정지·입력 누락을 해결하거나 부정행위를 검증하는 기능은 아니다.

진행 보고는 실제 시간으로 약 100ms마다 보낸다. 판정과 입력은 네트워크 쓰기나 응답을 기다리지 않는다.
게임 HUD에 최대 일곱 상대의 기준 시각과 내 점수 차이를 표시한다. 여러 명의 공통 시각 순위 집계는 별도 UI 범위다.

## 메시지와 상태

`GET /health`는 version 6과 status를 반환한다. `GET /api/rooms`는 방 요약, `GET /ws`는 JSON text WebSocket이다.
연결 첫 이벤트는 `welcome {version, player_id}`다. `hello {name}`으로 닉네임을 정한 뒤 방에 들어간다.
닉네임과 player_id는 인증된 계정이 아닌 해당 연결의 정보다.
요청 `id`(최대 64바이트)는 ack/error의 상관관계 값이며, room 스냅샷과 ack는 독립적으로 처리한다.

| 요청 | 주요 필드 |
|---|---|
| hello / list / clock | name / 없음 / sent_ns |
| create / join / leave | name, capacity, password(선택) / room_id, password(비밀번호 방) / 없음 |
| select | selection |
| ready | ready, revision, chart_hash, offset_ns |
| have | has_chart, revision, chart_hash (로컬 목록의 보유 여부) |
| propose | selection (한 사람당 최신 제안 하나) |
| ticket | revision (대기실 연결만 요청 가능, 응답 token) |
| attach | token, room_id, revision (게임 연결만 사용) |
| wait | match_id (플레이 포기, 방 연결 유지) |
| cancel | 없음 (방장만 준비/예약 취소) |
| start | 없음, 방장만 가능 |
| armed | match_id, start_ns |
| progress / finish | match_id, sequence, position_ns, score_at_ns, score |
| abort / reset / kick | match_id / 없음 / player_id |

clock 응답은 `clock {client_sent_ns, server_recv_ns, server_sent_ns}`와 `server_ns`를 담는다.
room은 `start_ns`, `arm_by_ns`, `end_ns`, 표시용 UTC start_at/deadline, 참가자 armed 상태를 담는다.
참가자 점수는 `position_ns`(오디오/게임 시각), `offset_ns`, `score_at_ns`(원본 판정 시각)로 구분한다.

selection은 title, chart_hash, lanes, rules, score_version, begin_ns, duration_ns, judgements, rate, mods를 담는다.
해시는 `Chart.Digest()`, 규칙은 `piano.Rules`, 점수 버전은 `piano.RecordVersion`이다.
begin은 -30초~0초, duration은 0초 초과~30분, 판정 수는 1~1,000,000, 배속은 0.5~2.0배다.
네이티브는 동일한 원본 채보·레인·규칙·점수 버전·배속·Mods·PCM 길이에서 선택 정보를 계산하여 비교한다.
공통 lead-in/end에는 허용된 개인 판정 오프셋 범위도 반영한다. 선택 변경/reset은 revision을 올리고 준비를 해제한다.

sequence는 참가자별 매 경기 증가한다. position은 감소·종료 위치 초과를 거부하며,
서버 시간보다 250ms 이상 앞선 위치를 거부한다. 이 값은 보고 검사 여유이지 싱크 정확도 아니다.
score_at은 position-offset과 일치해야 한다. `Score.Validate`와 판정 개수·누적 점수의 단조 증가를 검사한다.
finish에는 모든 판정 완료와 정확한 종료 위치가 필요하고, 부분 종료는 abort/left로 처리한다.
진행 점수는 잠정값이다. 기준 채보를 지정한 서버는 finish의 리플레이로 결과를 재계산한다.

일반 요청은 16KiB, 기준 채보를 지정한 서버의 종료 리플레이는 32MiB로 제한한다.
연결당 초당 40요청, 출력 큐 64개, 클라이언트 입력 큐 128개로 제한한다.
큐가 밀리면 연결을 종료하며 상태 메시지를 조용히 버리지 않는다. 단일 reader/writer와 명시적인 Close를 유지한다.
서버는 20초마다 ping, 60초 pong 제한, 5초 쓰기 제한을 적용한다. Ctrl+C는 WebSocket과 HTTP를 종료한다.

## 테스트 화면과 검증

`http://127.0.0.1:8090/`는 프로토콜 테스트 화면이며 실제 게임을 실행하지 않는다.
두 창에서 접속→방 생성/참가→선택→로드한 해시 입력→준비→시작→테스트 점수 전송으로 확인한다.
새 시계 교환과 예약 확인은 자동 처리하며, 표에 같은 시각의 점수 차이를 표시한다.
이 화면의 점수는 가상 테스트 채보의 시뮬레이션 값이다.
기준 채보가 있는 서버에서는 가상 점수 전송 버튼을 사용할 수 없다.

## 종료 결과 검증

```powershell
.\build\bin\multi.exe -addr 127.0.0.1:8090 -songs songs
```

`-songs`는 서버가 신뢰하는 원본 채보 폴더다. 시작 시 채보를 고정하고, 선택 시 해시·레인 수·
판정 수·시작/종료 위치를 확인한다. 서버 폴더에 없는 채보는 선택할 수 없으며 서버 채보당
최대 100,000판정이다. 오디오 끝 위치를 맞추려면 서버에도 같은 음원 에셋이 있어야 한다.

방의 `verify_results`가 true이면 네이티브 게임이 finish에 `replay`를 첨부한다.
서버는 경기 ID, 준비 시 확정한 오프셋, Mods, 종료 위치를 대조하고 최대 400,000개 입력을
공유 `piano.Session`으로 재판정한다. 재계산은 방 잠금 밖에서 수행하며 커밋 직전에 경기 상태를 다시 확인한다.
불일치 보고는 거부하고 이전 정상 점수·순서·상태를 유지한 스냅샷을 요청자에게 보낸다.
통과한 종료 결과에만 참가자의 `verified`가 true가 되고 다음 경기에는 초기화된다.

`-songs`가 없으면 기존 잠정 결과 방식이며 `verified`는 false다. 이 표시는 서버 채보와 입력의
일관성을 뜻한다. 위조 입력, Auto 사용, 실제 키보드 입력 여부, 실제 재생 배속까지 증명하지는 않는다.
계정 인증·공식 랭킹·부정행위 제재는 이 서버에 구현되어 있지 않다. 구버전 클라이언트는 프로토콜 4로 갱신해야 한다.

```powershell
go test ./...
go vet ./...
node --check internal/server/multi/static/client.js
pwsh scripts/checkmulti.ps1
```

검증 스크립트는 `build/bin/multi.exe`와 `build/bin/game.exe`를 사용하여 임시 로컬 서버와 실제 게임 두 개를 실행한다.
둘 다 Auto지만 한쪽에는 80ms 개인 오프셋을 준다. 공통 예약·최종 ack·110만점·원본 시각의 점수 변화 이력과
상대 시각 비교를 검사한다. 생성한 세 프로세스만 정리하며 보고서·점수·PNG는 `artifacts/11-multiplayer/`에 보관한다.
`-multi-report`는 QPC 예약/첫 Update/지연/RTT/불확실성/드리프트·시각별 점수 변화·비교 결과를 저장한다.

2026-10-09 대기실 구현 후 네이티브 로컬 실행에서 두 게임은 동일 경기/시작 시각으로 완료했고, 비교 109회·110회 모두 차이 0이었다.
예약 대비 첫 Update 지연은 15.45695ms·2.9445ms, RTT는 0.1149ms·0.13ms였다.
0ms/80ms 오프셋의 실제 점수 변화 시각·값도 일치했다. 최초 zero 이력 시작 시각은 개인 오프셋만큼 다르므로
동일성 검사는 판정이 발생한 변화 이력을 대상으로 한다. 위 수치는 같은 Windows PC의 두 프로세스 측정이다.
오디오 음량은 0으로 했으며 실제 음향 출력 오차나 인터넷·다른 PC의 싱크 정확도를 측정한 결과가 아니다.

전체 Go 테스트·vet, 서버/게임 빌드, WASM 회귀 빌드, JS 구문 검사와 frontend 스타일 검사를 통과했다.

대기실의 보유자 자동 참가·채보 없는 대기자·도중 입장·곡 제안 권한·게임 티켓 재사용 거부·
게임 연결 종료 후 방 유지·방장 승계·로딩 타임아웃은 WebSocket 통합 테스트로 검증했다.
Wails 개발 브라우저의 실제 Go 바인딩으로 게임을 두 차례 완주하고 같은 방에서 재실행했으며,
시작 예약 직후 **플레이 포기 · 대기실**을 눌러 미완주 결과로 정상 종료하고 방을 유지하는 것도 확인했다.
이는 한 Windows PC에서의 검증이며 여러 PC의 네트워크·실제 음향 동시성 검증은 아니다.
시계 큐 지연 제외·표본 만료·비대칭 불확실성·예약 누락/지연 취소·과거 이력 조회·동시 판정·개인 오프셋·
완주 이후 최종 점수와 기존 방/권한/퇴장/종료 경로도 검사했다. race 검사는 cgo 비활성 상태라 실행하지 못했다.

Windows 전역 Go 캐시에 쓰기 권한이 없으면 같은 PowerShell에서 아래 변수를 설정한다.

```powershell
$cacheRoot = Join-Path (Get-Location) '.cache'
$env:GOMODCACHE = Join-Path $cacheRoot 'mod'
$env:GOCACHE = Join-Path $cacheRoot 'build'
$env:TEMP = Join-Path $cacheRoot 'tmp'
$env:TMP = $env:TEMP
```

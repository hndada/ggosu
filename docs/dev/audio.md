# 오디오 로딩 측정

## 상주 게임 프로세스

데스크톱 메뉴는 `game.exe -resident`를 한 번 시작하고 곡마다 요청을 보낸다. 곡 선택의 사전 로딩 요청에서 숨긴 게임 창을 먼저 준비하며, 바로 Play를 누른 경우에는 그때 시작한다. Ebitengine 루프·그래픽 드라이버·창과 이미 생성된 오디오 context를 유지한다. 곡 완료 메시지는 결과 저장과 곡별 자원 정리 후 전달하며, 메뉴 복귀 시 프로세스는 종료하지 않는다. 대기 중에는 필요할 때만 Update/Draw를 실행한다. 메뉴 종료 또는 입력 파이프 단절은 프로세스를 종료시킨다.

2026-10-12 실제 One Sided Love Easy의 PCM 캐시를 준비한 상태에서 첫 Draw까지 3회 측정했다. 매번 새 프로세스를 시작하면 734~764ms, 상주 프로세스에 요청하면 153~166ms였다. 중앙값은 753ms에서 157ms로 약 79.1% 줄었다. 상주 프로세스 자체의 최초 준비는 별도로 621ms였다. 초기 디코딩과 250ms 플레이 전 여유 시간은 이 비교에서 제외한다. 측정 자료와 검증 범위는 [보고서](../../artifacts/38-resident/report.md)를 참고한다.

게임은 첫 화면 전에 채보의 음원을 PCM으로 준비한다. O2Jam처럼 짧은 Ogg 키음이 수백 개 있는 곡에서는 파일 읽기보다 샘플레이트 변환이 시작 시간을 크게 차지했다.

2026-10-11, Ryzen 7 7800X3D에서 One Sided Love의 파일 읽기는 8.3ms, M30 해독은 12.7ms, 원본 샘플레이트의 Vorbis 디코딩은 2.93초였다. 기존 48kHz 변환을 포함한 오디오 로딩은 23.88초였다. CPU 프로파일의 주요 비용은 Ebitengine 스트림 리샘플러의 필터 계산과 샘플 조회였다.

`internal/play/resample.go`는 같은 필터·코사인 표·클리핑·정수 변환 순서를 사용한다. 원본 PCM을 한 번 디코딩한 후 소수 위치별 필터 계수를 재사용하고, 32프레임 링에 정규화한 샘플을 보관한다. 계수 캐시는 음원 하나당 4,096개로 제한한다. 디코딩 출력 버퍼는 알려진 길이만큼 미리 확보하고 코덱에는 32KiB씩 전달한다.

최적화는 Ogg·WAV·MP3 로딩 경로에 적용한다. 길이를 알 수 없거나 원본 PCM이 512MiB를 넘으면 출력 한도를 둔 스트림 경로를 사용한다. 뱅크에 보관하는 PCM의 기존 512MiB 제한을 유지하며, 원본 PCM은 변환 중에만 필요하다. 전체 프로세스의 최대 메모리는 이 보관 한도와 별개다.

## 확인 결과

같은 조건에서 음소거·Easy·Auto로 실행한 **프로세스 시작부터 첫 화면의 `ready` 신호까지** 시간이다. 실행마다 PCM을 새로 디코딩하며, 영구 PCM 캐시는 사용하지 않는다. 파일 시스템 캐시를 비우는 실험은 아니다.

| 곡 | 이전 | 수정 후 |
|---|---:|---:|
| Spring Symphony | 13.85초 | 4.50초 |
| One Sided Love | 20.01초 | 5.53초 |

오디오 로딩 벤치마크의 One Sided Love는 수정 후 4.30초였다. 측정된 첫 화면 시간에는 창·화면 초기화도 포함된다. 보관된 측정 자료는 [보고서](../../artifacts/28-audio-load/report.md)를 참고한다.

두 곡에서 참조한 저장 키음 1,697개의 PCM 총 228,797,780바이트가 기존 `vorbis.DecodeWithSampleRate` 결과와 완전히 같았다. 별도 회귀 테스트는 여러 샘플레이트, 빈 입력, 짧은 입력, 버퍼 경계, 서로 다른 스테레오 값과 메모리 제한을 확인한다. 실제 창 검증은 음소거로 2초 실행했으며, 청감 평가나 네이티브 완주 검증은 포함하지 않는다.

## 재측정

```powershell
$env:GGOSU_BENCH_CHART = 'C:\Music\song.ojn'
go test ./internal/play -run '^$' -bench '^BenchmarkBank$' -benchtime=1x -count=1

# 여러 채보의 원래 PCM과 바이트 단위로 비교한다.
$env:GGOSU_BENCH_CHART = 'C:\Music\first.ojn;C:\Music\second.ojn'
go test ./internal/play -run '^TestRealBankPCM$' -count=1 -v
Remove-Item Env:GGOSU_BENCH_CHART
```

일반 테스트에서는 실제 곡 경로가 필요한 테스트와 벤치마크를 건너뛴다. 표준 입력으로 수행하는 리샘플러 회귀 테스트는 항상 실행한다.

## 2026-10-12 추가 개선

네이티브에서 서로 다른 키음 최대 4개를 동시에 디코딩한다. 코덱 리더·PCM은 작업별로 분리하고 오디오 플레이어와 결과 맵은 로딩 goroutine에서 처리한다. 배치의 각 작업은 남은 보관 PCM 한도를 나눠 사용하고, 큰 샘플은 작은 샘플들을 반영한 뒤 남은 한도로 순차 재시도한다. 같은 경로·뱅크 샘플의 별칭은 한 번 읽고 같은 PCM을 공유한다. 배치 작업은 전부 종료한 뒤 로딩이 반환한다. WASM은 단일 디코딩 작업을 유지한다.

One Sided Love Easy의 오디오 준비 벤치마크 3회 중앙값은 순차 5.485초에서 병렬 2.988초로 약 45.5% 줄었다. WAV 44.1kHz 200ms 합성 샘플은 기존 스트림 변환 3.839ms에서 계수 재사용 0.625ms로 줄었다. 이것은 디코딩·뱅크 로딩 구간 측정이며 전체 첫 화면·청감·GPU 성능 측정과 다르다. WAV 회귀 검사는 여러 소스 주파수에서 이전 디코더와 PCM 바이트가 같은지 확인한다. 로그는 `artifacts/31-hud-feedback/`에 보관한다.

## 지속 PCM 캐시와 사전 로딩

네이티브 게임은 변환한 48kHz stereo 16-bit PCM을 디스크에 저장한다. 데스크톱 메뉴는 `data/cache/pcm`을 사용하고 CLI는 기본 사용자 캐시 폴더의 `ggosu/pcm` 또는 `-cache <경로>`를 사용한다. 음원 경로·크기·수정 시각과 캐시/디코더 버전으로 무효화한다. 키음은 원본 경로와 뱅크 샘플 번호 기준으로 같은 곡의 난이도들이 공유한다. 배속·Pitch·판정은 캐시 키와 PCM을 바꾸지 않는다.

샘플별 체크섬을 확인하며, 필요한 샘플이 없거나 캐시가 손상되면 원본을 디코딩한다. 임시 파일을 완성한 후 원자적으로 교체하고, 최근 사용한 순서로 오래된 캐시를 지워 총 2GiB를 목표로 제한한다. 현재 사용하는 파일은 보존한다. 캐시 읽기·쓰기 실패는 게임 진행이나 점수 자격에 영향을 주지 않는다.

곡 선택이 600ms 유지되면 Wails가 창과 오디오 재생 없이 `game.exe -warm`을 실행해 모든 난이도의 키음을 준비한다. 다른 곡을 선택하거나 플레이를 시작하거나 클라이언트를 닫으면 작업을 중단하고 종료를 기다린다. 사전 로딩을 완료하지 못한 첫 플레이는 원본 디코딩으로 이어진다. 브라우저 WASM은 기존 메모리 로딩 경로를 사용하며 이 네이티브 디스크 캐시를 사용하지 않는다.

2026-10-12 같은 실제 One Sided Love 채보를 무음으로 3회 측정했다. 직접 디코딩 중앙값 2.245초, PCM 캐시 로딩 중앙값 0.09152초로 약 95.9% 줄었다. 누적 할당량도 약 1.225GB에서 135MB로 감소했다. 파일 경로 검증은 음원 파일당 한 번 수행한다. 이 값은 오디오 준비 시간이며 프로세스 생성·창 표시·첫 Draw까지의 전체 시간을 뜻하지 않는다. 자료: `artifacts/33-cache-o2jam/cache-bench.txt`, `cache-fast.txt`.

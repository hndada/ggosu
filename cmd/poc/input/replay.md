# 게임 시간 입력 기록과 리플레이

네이티브 입력 POC(`cmd/poc/input`)에서 D/F/J/K의 누름·해제를
1.0배속 기준의 고정된 게임 시간축에 저장하고 재생한다.
이 문서의 조작·OS 입력 설명은 입력 POC 기준이다. 곡 선택창의 `cmd/game`은
채보 해시·판정 규칙·레인 번호를 가진 `lane-index` 기록을 결과와 함께 저장한다.
Mods·개인 프로필·오프셋·초기 배속의 복원 범위는 [플레이 옵션](../../../docs/guide/play-options.md)을 참고한다.

```powershell
.\build\poc\inputpoc.exe -record artifacts\input.json
.\build\poc\inputpoc.exe -replay artifacts\input.json -playback 0.5
```

`-record`와 `-replay`는 함께 지정할 수 없다. 기록은 Esc 또는 창 닫기로 정상
종료한 뒤 저장한다. 기존 경로를 지정하면 기존 파일을 교체한다. 임시 파일에
인코딩하고 닫은 뒤 옮기므로 쓰기 실패로 기존 파일을 잘라내지 않는다.
큐 누락·수신 순서 오류·실행 오류가 있으면 성공한 기록으로 저장하지 않는다.

| 조작 | 동작 |
|---|---|
| D/F/J/K | 라이브 플레이 레인 입력. 리플레이 중에는 레인에 적용하지 않음 |
| P | 게임 시간 일시정지/재개 |
| F7 | 배속 0.5 → 1 → 1.5 → 2 → 0.5 순환 |
| `-playback` | 시작 배속 지정. 양의 유한한 수 |

정지 중 F7로 변경한 배속은 재개할 때 적용한다. 정지·배속 제어는 네이티브
입력의 수신 순서대로 처리하므로 한 Update에 여러 변경이 쌓여도 구간을 구분한다.

## 시간 기준

`internal/clock.Counter`의 QPC 시간은 입력 수신과 지연 측정에 계속 사용한다.
별도의 `clock.Timeline`은 시작 지점과 배속 변경 지점을 보관한다.

저장된 시각의 기준은 항상 1.0배속이다. 예를 들어 2배속 플레이에서 실제 5초에
발생한 입력은 게임의 1배속 기준 위치인 10초로 기록한다. 동일한 게임 위치의
입력은 기록할 때의 배속이 1배속이든 2배속이든 같은 값이다.
저장값을 재생 배속으로 다시 곱하거나 나누지 않는다.

```text
구간 내 게임 시각 = 구간 시작의 게임 시각 + (QPC 시각 - 구간 시작 QPC 시각) × 배속
일시정지 = 배속 0
```

변경 시 이전 구간의 끝과 새 구간의 시작을 일치시켜 게임 시간이 연속되도록 한다.
`Position(event.At)`은 수신 당시 구간을 조회한다. 처리 시점의 배속을 과거 입력에
곱하거나 프레임/TPS로 수신 시각을 대체하지 않는다. 시각의 정밀도는 QPC의 수신
관측 정밀도이며 물리적 키 동작 시각을 보장하지 않는다.

원래 플레이의 정지 길이와 배속 조작 이력을 리플레이 파일에 넣지는 않는다.
각 입력이 발생한 **게임 내 위치**를 재현하며, 재생할 때의 정지와 배속을 별도로
적용한다. 예를 들어 게임 시각 2초의 입력은 2배속에서 실제 시간 약 1초에 재생된다.
게임 시각 1초에서 5초 동안 정지하면 이후 입력도 실제 시간에서 5초 늦춰진다.
리플레이 중간에 배속을 바꾸면 그 위치부터 시계의 진행 속도만 바뀐다.
예를 들어 1배속으로 실제 6초까지 재생하고 2배속으로 바꾸면, 게임 시각 10초의
입력은 실제 8초에 실행된다. 정지 기간만큼 실제 실행 시각은 추가로 늦춰진다.

## 기록 형식

```json
{
  "version": 2,
  "key_encoding": "windows-vk",
  "time_base": "game-1x",
  "duration_ns": 1000000000,
  "events": [
    { "at_ns": 500000000, "key": 68, "down": true },
    { "at_ns": 500000000, "key": 68, "down": false }
  ]
}
```

시각은 정수 나노초이며 `key`는 Windows virtual-key 값이다. D/F/J/K는
각각 68/70/74/75다. 배열 순서가 같은 시각의 이벤트 순서를 결정한다.
프레임 사이에 누름과 해제가 모두 발생해도 둘 다 보존한다. OS 자동 반복 누름,
제어 키, 합성 부하 입력은 플레이 기록에 넣지 않는다.

`time_base`는 반드시 `game-1x`다. 다른 시간 기준의 파일은 거부한다.
기존 version 1 파일도 같은 게임 시간축을 사용했으므로 읽을 때 version 2로
인식하며 시각 값은 그대로 유지한다. 새로 저장하는 파일에는 시간 기준을 명시한다.

라이브 정지 시 눌린 레인을 그 게임 시각에 해제하고 기록한다. 정지 중 레인 입력은
버린다. 정지 전부터 유지한 키는 재개 후 떼었다 다시 눌러야 새 입력으로 인정한다.
포커스 상실이 Update에서 감지된 경우와 정상 종료 시에도 유지한 레인을 해제한다.
포커스 상실 자체는 P와 같은 명시적 게임 시간 정지로 취급하지 않는다.

리플레이 중 P로 정지하면 현재 리플레이 키 상태를 유지한다. 정지 경계까지 도달한
입력은 소비하지만 그 뒤의 입력은 게임 시간이 다시 진행할 때 소비한다.
리플레이에 제어 입력이 늦게 전달되면 이미 소비한 시각보다 앞선 위치로 되감지 않도록
직전 Update의 시계 표본 이후에 적용한다.

## 소비 API와 범위

`rules.ReadReplay`/`WriteReplay`는 버전·키 표현·시각 범위·순서를 검사한다.
`replay.NewPlayer(file)`은 이벤트를 복사해 소유하고,
`AppendDue(dst, gamePosition)`은 그 시각까지 도달한 전이를 한 번씩 반환한다.
멈춘 같은 시각으로 반복 호출해도 중복되지 않는다. `Done()`은 마지막 입력 소비
여부이며 곡 종료 여부는 아니다.

```go
due, err := player.AppendDue(due[:0], timeline.Position(counter.Now()))
if err != nil {
    return err
}
for _, e := range due {
    // 판정 등에 e.At을 그대로 사용하고, 각 누름/해제를 순서대로 적용한다.
}
```

되감기/seek는 자동 지원하지 않는다. `Reset()` 후 게임 상태도 초기화해 처음부터
소비해야 한다. 이 POC는 음악 재생·채보·판정·곡 식별을 포함하지 않으며 화면 레인에
입력을 적용한다. 향후 음악을 연결하면 음악의 재생 위치와 게임 시계가 같은 시간
기준을 사용하도록 연결해야 한다. OS/Ebitengine 키 상태에 리플레이를 주입하지 않는다.

## 검증

단위 테스트는 정지·재개·배속 변경, 변경 전 수신된 입력의 지연 처리,
같은 시각의 누름/해제 순서, 다른 배속의 재생, 반복 소비, 지연된 정지 제어,
정지 경계 소비, 키 유지 정책, 파일 왕복과 누락 시 저장 거부를 검사한다.
1배속·2배속 기록의 동일한 저장값과 파일을 읽은 뒤 재생 중 1 → 2 → 정지 →
2 → 0.5배속으로 변경하는 경우도 검사한다. 저장 파일과 소비된 입력의 시각이
배속 변경으로 바뀌지 않는 것을 확인한다.

```powershell
$env:GOMODCACHE = Join-Path (Get-Location) '.cache\mod'
$env:GOCACHE = Join-Path (Get-Location) '.cache\build'
$env:TEMP = Join-Path (Get-Location) '.cache\tmp'
$env:TMP = $env:TEMP
New-Item -ItemType Directory -Force $env:TEMP | Out-Null
go test ./...
go vet ./...
go build -o build\poc\inputpoc.exe ./cmd/poc/input
```

2026-10-07 검증 결과:

- `go test ./...`, `go vet ./...`, 입력 POC 빌드 통과.
- 실제 GUI에서 리플레이 fixture를 0.5배속으로 소비하며 100ms Draw 지연과
  24,000개 합성 이벤트를 처리했다. 게임 시각 약 1.7초에서 8개 중 7개만 소비하고,
  게임 시각 2초의 K 해제는 기다리는 것을 JSON 보고서와 PNG에서 확인했다.
- 같은 fixture의 2배속 소비도 별도로 확인했다. 실행 결과는 로컬
  `artifacts/02-replay/replay-check.*`, `artifacts/02-replay/replay-fast-check.*`에 있다.
- OS 입력 자동 검사는 POC 창이 전면이 아니어서 8개 입력을 보내지 못했다.
  물리 키보드의 P/F7 제어는 직접 확인하지 않았다. 정지·재개와 배속 변경의
  시간 변환·소비 정책은 단위 테스트로 검증했다.
